## Section 1: Executive summary

### 1.1 Overall condition

**Meta — sound architecture, two material gaps.** The integration is a textbook redundant setup: one browser-generated `event_id` per event on both halves, server Purchase rebuilt from the order and delivered exactly once through a leased ledger, worldwide normalisation shared by both halves, HTTP-minted `_fbp` / `_fbc` / external id cookies (Safari-safe), identity bound to the visitor to prevent shared-device leakage, consent plumbing (off by default), and a 15-minute retry/recovery job. The 28 fixes landed on 2026-10-27/28 (PRs #31–#34) removed the issues that most damaged match quality (CSP blocking every Pixel event carrying Advanced Matching, the pre-login InitiateCheckout, session expiry treated as logout, carrier IP as client IP, single-value identity). What remains, verified in code: (a) the Purchase retry path cannot tell a revoked token or platform outage from a bad event, has no backoff, and permanently closes a Purchase after five failed cron runs (~75 minutes) — a durable-delivery gap, not a daily loss; (b) the admin "Test connection" button sends a synthetic PageView with an invented `test_event_code`, which Meta documents as counted in reporting and audiences; (c) a second Razorpay webhook endpoint never emits the Meta Purchase (the cron recovers it ≥20 minutes later); (d) native-app WebView pages marked `?zb_app=1` suppress the Pixel but still relay server events.

**Snapchat — sound, with the identity/coverage gaps fixed this week.** Same architecture, same ledger, Snap-specific names and fields, `client_dedup_id ⇄ event_id` on every event and `transaction_id ⇄ order_id` on PURCHASE, `ScCid` / `_scid` now minted as HTTP cookies, the server half now carries the same bound identity as the pixel half, logged-in init carries name and phone, `external_id` sent as a string per Snap's reference, country-only IP geo, per-visitor rate limit, internal/bot exclusion. Remaining, verified in code: the first PAGE_VIEW of a fresh login session has identity on the pixel half but not the server half; relay schema caps (search string, item counts) are not mirrored client-side so an over-cap event loses its server half silently; product-page PAGE_VIEW carries no `item_ids` although Snap's Dynamic Ads requirements list it; SIGN_UP lacks `sign_up_method`; the CAPI token travels in the query string (documented but avoidable).

**Cross-platform isolation: clean.** No Meta field reaches Snap or vice versa; shared code is generic (normalisation, cookies, admission, ledger) and the vendor rules that differ (hashing of `external_id`, raw `sc_*` ids, event names, pixel identity parameters) are applied in the vendor senders. See Section 7.

### 1.2 Most serious risks (ordered)

1. **M-C2 — Meta Purchases can be permanently lost during a token/platform incident.** `sendCapiEvent` returns a bare failure for every 4xx/5xx/timeout; the ledger consumes an attempt each time; the cron retries at a fixed 15-minute cadence; at 5 attempts the row is closed `skipped` and a manual SQL reset is the only recovery. A revoked token (Graph code 190) for ~75 minutes loses every Purchase captured in that window. [code]
2. **M-C9 — Synthetic admin events counted as real.** Every dashboard "Test connection" click sends a PageView with `client_ip_address: 127.0.0.1`, UA `Meta-Connection-Test/1.0` and `test_event_code: CONNECTION_TEST_<ts>`; Meta states test-coded events "are not dropped" and are used for measurement. Low volume, but it is a confirmed noise source and the diagnostics GETs put the access token in URLs. [code] [docs]
3. **Unverified live quality.** EMQ per event, Event-coverage %, dedup rates, Snap EQS, Click-ID return rate and the `fbp` parameter on live Pixel hits could not be read (no Events Manager / Snap Events Manager access; no production tokens locally). The code-level audit cannot replace those readings. [unverified]
4. **M/S-C1 — App WebView pages produce server-only website events.** `?zb_app=1` sets an in-memory flag only; relays see no cookie and still send PageView/VIEW_CONTENT with `action_source: website` from app sessions, with no pixel pair. [code]
5. **M-C3 — Asymmetric webhooks.** `app/api/payments/webhook` marks orders paid and emits the Snap Purchase but not the Meta Purchase; recovery depends on the cron scan (≥20 min). Delay, not loss, provided a ledger row/context exists. [code]

### 1.3 Key unknowns

- Actual EMQ / match-key coverage / event coverage / dedup overlap on Meta; EQS per event and per source on Snap; Click-ID return rate; "Additional conversions reported". Need Events Manager (Meta) and Snap Events Manager, or the Dataset Quality API (Meta, system-user token) and Signal Readiness API (Snap, CAPI token).
- Whether the live Pixel sends `fbp` (the local build with a dummy pixel id omitted it; the SDK's first-party-cookie behaviour is configured in Events Manager → Settings → Cookie settings).
- Whether the Meta `client_user_agent` requirement rejects webhook/cron Purchases that have no recorded context (M-H4) — needs an `fbtrace_id` from a live rejection.
- Which duplicate copy Snap retains and whether Snap de-duplicates two server copies with the same `event_id` (S-H1).
- Whether the GTM container (`GTM-WKTQJ5LF`) is still empty (it was on 2026-10-15); any vendor tag added there would duplicate events.

### 1.4 Highest-priority recommendations (details in Section 8)

P0: classify Meta send errors (190/102/200/4/17/613/80004/5xx/timeout → `blocked` or retryable without consuming attempts), add backoff, alert on `blocked`; stop the admin connection test from sending a real-looking event (use the Payload Helper / `/validate`-style check, or a dedicated test dataset) and move its token out of URLs. P1: have `?zb_app=1` set the `zb_internal`-style exclusion (or a dedicated `zb_app` cookie) so relays skip too; add `emitMetaPurchase` to the second webhook; mirror relay caps client-side; send identity on the first logged-in PAGE_VIEW; add `item_ids` to product-page PAGE_VIEW for Snap DPA; `sign_up_method` on SIGN_UP. P2: Bearer header for Snap, cross-reload guard for AddPaymentInfo, Meta `<noscript>` fallback, consider Automatic Advanced Matching (Meta) and Automated Matching (Snap) in the dashboards. P3: Dataset Quality API + Signal Readiness API polling, ledger retention, cosmetic/log hygiene.

## Section 4: Existing architecture

### 4.1 Overview

The storefront is a Next.js 14 app (App Router) on DigitalOcean App Platform behind Cloudflare, with Shopify (Admin API) as the catalogue, Razorpay for payments and Postgres (Prisma) for orders. Both ad platforms are integrated the same way, as two separate pipelines that share only generic infrastructure (identity cookies, normalisation helpers, the delivery ledger):

1. **Browser pixel** — an inline queue stub per vendor in `app/layout.tsx` (fbq / snaptr) runs before any script, so early `track()` calls queue; the vendor SDKs (`connect.facebook.net/en_US/fbevents.js`, `sc-static.net/scevent.min.js`) are injected after `window.load`.
2. **Browser → relay → Conversions API** — every funnel event is also POSTed by the browser to a first-party relay (`/api/meta/event`, `/api/snap/event`) that enriches it with request metadata and the visitor's first-party cookies and forwards it to the vendor's Conversions API. The browser generates one event id per event and sends it to both halves.
3. **Order → ledger → Conversions API (Purchase)** — the server Purchase is never built from browser input: it is rebuilt from the stored order and delivered exactly once through the `AdConversionDelivery` ledger (one row per platform × event × order, claimed with a lease), from three entry points (checkout completion, Razorpay webhooks, a 15-minute retry/recovery cron). The browser fires the Purchase pixel only, with the order id as the dedup key.

### 4.4 Potential conflicts and duplicate implementations

- **Two Razorpay webhook endpoints** (`app/api/webhooks/razorpay`, `app/api/payments/webhook`) both process `payment.captured`; only the first emits the Meta Purchase, both emit Snap. Delivery is idempotent through the ledger, so the duplication cannot double-send; the asymmetry delays Meta Purchases from the second endpoint until the cron recovery scan (M-C3).
- **Three identity writers** (checkout, login enrichment, newsletter) all go through `saveUserDataToCookies`, which binds to the current external id; no competing cookie formats were found.
- **Shared ledger** (`lib/snap/ledger.ts`) is used by both platforms with distinct `platform` keys; semantics differ only in the senders (Snap returns `blocked`, Meta never does, M-C2).
- **Shared normaliser** (`lib/tracking/identity-normalize.ts`) is used by both; both vendors' documented rules (lowercase email, E.164 digits without `+`, ISO-2 lowercase country, SHA-256 lowercase hex) are identical for the fields in use, so the sharing is correct (Section 7).
- **No second pixel loader**: GTM (`GTM-WKTQJ5LF`) is loaded on the storefront but the container was found empty in the Phase-1 audit; no vendor tag is duplicated through GTM (unverified since 2026-10-15; re-check the container before launching anything there).
